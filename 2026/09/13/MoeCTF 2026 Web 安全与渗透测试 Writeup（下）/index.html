1. 熊出没（100 分）

MoeCTF 2026 · Web 安全与渗透测试 · 100 分
题目：熊出没（两只小熊在狗粉岭找蜂蜜，发现许多蜜罐，但有些是猎人设的陷阱。蜂蜜在 54321 端口）

打开题目是一个「狗粉岭」网页，中间一个表单让你输入「蜜罐地址」，提交后服务器帮你去「看看是不是真的蜂蜜」。

表单 POST /fetch，参数 url——服务器按你给的 URL 去抓内容，这明显是一个 SSRF（服务端请求伪造） 端点。SSRF 指攻击者让服务器代替自己去发起网络请求，从而访问攻击者本来访问不到的目标：普通用户只能从「外部」访问网站，但服务器往往在内网，能访问内网里不对外暴露的服务（数据库、缓存、内部 API）。如果网站有个「按用户给的 URL 去抓内容」的功能，就能传一个内网地址让它帮忙访问，再通过回显把结果带出来。

顺着提示「蜂蜜在 54321 端口」，先试 http://127.0.0.1:54321/，结果返回的是一堆随机出现的「陷阱」提示（🐝 愤怒的蜂群、🍯 陷阱蜜、🪤 假蜜罐、🐻 捕兽夹）。这正是**蜜罐（Honeypot）**的思路：故意布置看起来像真目标、实则用来迷惑攻击者的假服务或假数据。这里的随机陷阱文案说明服务器并没有真正用 HTTP 抓到 54321 的内容，而是把我们挡在了外面。

这就要理解 JavaScript 的对象模型了。JS 的继承机制和 Java/C++ 不一样，是基于原型（prototype）的：每个对象都有一个内部指针指向它的「原型对象」，访问对象属性时，如果自身没有，就顺着这条原型链一路向上查找，直到找到或到达 null。所有普通对象最终都指向同一个原型 Object.prototype——这意味着往 Object.prototype 上添加一个属性，等于给所有对象都「继承」了这个属性。config.isAdmin 之所以是 null，就是 config 自身没有，顺着原型链从 Object.prototype 查到的（默认没有）。

于是思路清晰了：服务器读 config.isAdmin 和 config.canReadFlag，这俩属性不在配置对象自身身上、是从原型继承来的；只要往 Object.prototype 上注入 isAdmin=true 和 canReadFlag=true，审核自然通过。这就是原型链污染（Prototype Pollution）：程序允许攻击者控制「给对象添加属性」的键名且不做过滤时，把键名设为 __proto__，就能把属性写到 Object.prototype 上、污染全局原型。

POST /api/profile 会把提交的 JSON 递归合并（Deep Merge） 进配置对象——即逐层合并，目标对象里没有的键就复制进去、值是对象则继续递归。它的危险性在于：如果合并时用 target[key] = source[key] 这种直接赋值，当 key 恰好是 __proto__ 时，target.__proto__ 会被当成普通属性赋值，结果污染原型。其中 __proto__ 是非标准但被广泛支持的原型访问器，指向对象的原型（对普通对象就是 Object.prototype），是污染攻击最常用的键名。

6. 黑市走私（250 分）

MoeCTF 2026 · Web · 250 分

「BLACK FLAG MARKET」黑市，flag 是禁售品，直接买会被「巡逻队」逮捕。页面给出四条路：

第一步：伪造 JWT

先认识 JWT（JSON Web Token）——一种紧凑、自包含的令牌格式，常用于身份认证，由三段用 . 连接、各自 base64 编码：header.payload.signature。header 描述算法（如 {"alg":"HS256"}），payload 存放声明（如 {"role":"admin"}），signature 是签名、防止内容被篡改。注意 JWT 本身不加密，payload 只是 base64 编码，任何人解码就能看到内容；它的安全性依赖签名验证。

/hint 里的普通入场券：

payload 解出来是 {"sub":"traveler","role":"guest","scope":"read"}。

JWT 的 HS256 算法就是 HMAC-SHA256：HMAC 是「带密钥的哈希」HMAC(key, message)，用密钥把消息哈希一遍，能同时提供完整性和认证（只有持密钥者才能算出正确签名）；HMAC-SHA256 就是用 SHA-256 做底层哈希。签名 = HMAC-SHA256(密钥, header.payload)。如果密钥太弱，攻击者就能拿候选词逐个算签名、和已知签名比对，命中即拿到密钥，之后任意伪造 token。

第二步：CL.TE 走私拿 /flag1

请求走私发生在「多级 HTTP 架构」里：请求先经过一个前端代理/负载均衡，再由它转发给后端服务器。根源是 HTTP 请求的「结束边界」有两种互相冲突的表示方式：

  • Content-Length（CL）：直接用数字标明 body 字节长度；
  • Transfer-Encoding: chunked（TE）：body 切成若干「分块」，每块前标一个十六进制块长度，最后以 0\r\n\r\n 结束，适合长度未知的流式传输。

当请求同时带这两个头时，不同实现会「优先相信谁」产生分歧——这就是走私的根源。如果前后端对边界理解不一致，后端可能把「一个请求」误判成「两个」：攻击者把第二个请求藏在第一个请求的 body 里，前端按 A 方式把整段转发、后端按 B 方式解析，就会把 body 里藏着的「走私请求」当成新的独立请求执行，从而绕过前端过滤。

黑商1 的暗号「先让柜台只看货箱长度，再让后仓按分块清点」→ 前端（柜台）用 CL、后端（后仓）用 TE，即 CL.TE（前.后 表示各自采用的解析方式）。

构造：一个 POST /stage1，同时带 Content-Length 和 Transfer-Encoding: chunked，body 里先写 0\r\n\r\n（chunked 结束），再塞进一段完整的 GET /flag1 请求。前端按 CL 把整段 body 原样转发；后端按 TE 解析，0 之后的内容被当成新的一个请求，直接处理 GET /flag1 并带上高级票据：

黑商2 的暗号「冒号前多了一粒灰」「Transfer-Encoding 后的空隙」→ 在冒号前加一个空格，把请求头写成 Transfer-Encoding : chunked（: 前有空格）。这是请求头混淆（Header Obfuscation）：HTTP 规范对头格式的宽容度，让前后端解析器常有差异——前端读到带空格的伪头，认不出这是 TE、退回用 CL；后端容忍空格、照常按 TE chunked 解析。本质还是 CL.TE，只是靠混淆让前端「看不见」TE。

小结：JWT 密钥 fish 可从提示候选词逐个比对签名得出，伪造 role=admin, scope=flags；前端代理拦 flag 关键词 → 用 HTTP 请求走私绕过；/flag1 用标准 CL.TE、/flag2 用 TE 头混淆（Transfer-Encoding : chunked 冒号前加空格）。走私的关键始终是：前后端对请求体边界理解不一致，导致后端把 body 里藏着的请求当成新的独立请求执行。
