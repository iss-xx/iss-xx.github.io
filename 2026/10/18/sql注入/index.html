一、SQL 注入到底是什么？

SQL 注入的本质只有一句话：用户输入变成了 SQL 代码的一部分。

这就是 SQL 注入：攻击者通过控制输入，改变原本 SQL 语句的语法结构，让数据库执行预期之外的查询[reference:1]。

SQL 注入不限于登录框。搜索、文章 ID、Cookie、X-Forwarded-For、甚至注册时的用户名，只要最终被拼接进 SQL，都可能是注入点[reference:2]。

二、先搞懂这几个 MySQL 底座知识

CTF 中的 SQL 注入绝大多数以 MySQL 为靶场，下面几个“底座”必须烂熟于心。

2.1 注释符

三、SQL 注入的分类：按“回显方式”来记最清晰

CTF 中不需要死记硬背分类名称，按页面给你什么反馈来选手法，是最实用的思路。

选择顺序通常是：有回显 → 联合查询；有报错 → 报错注入；无回显但有真假 → 布尔盲注；完全没反应 → 时间盲注。堆叠注入和二次注入属于特殊场景，后面单独讲[reference:6]。

3.2 报错注入（Error-based）：页面报错就是“回显”

前提：页面会显示数据库错误信息，但没有正常回显位。

核心函数是 updatexml() 和 extractvalue()，它们要求第二个参数符合 XPath 格式，如果不符合，就会把传入的内容作为错误信息抛出来[reference:8]。

0x7e 是 ~，加在数据两边是为了让错误信息更醒目。

updatexml() 和 extractvalue() 单次最多回显 32 个字符。数据较长时，用 substr() 分段读取，或者用 left() / right() 截取[reference:9]。

3.3 布尔盲注（Boolean-based）：页面只给你“是/否”

前提：页面不显示数据，也不显示报错，但“查询到结果”和“没查询到”的页面状态不同（比如 “登录成功” vs “用户名不存在”）。

3.4 时间盲注（Time-based）：页面完全“沉默”

前提：真假页面完全一样，没有任何视觉差异。

只能靠 sleep() 让数据库“卡住”，通过响应时间判断条件真假：

如果响应时间明显变长（约 3 秒），说明条件为真；立刻返回，说明条件为假[reference:10]。

3.5 堆叠注入（Stacked）：一次执行多条语句

前提：数据库驱动支持多语句执行（MySQL 中 PHP 的 mysqli_query 默认不支持，但 PDO 某些配置或 CTF 环境可能开放）。

堆叠注入的杀伤力在于可以执行 INSERT、UPDATE、DELETE，甚至 SELECT ... INTO OUTFILE 写文件[reference:11]。

3.6 二次注入（Second-order）：输入先“存起来”，后“炸出来”

原理：用户输入在存入数据库时被安全转义了，但在后续的查询中，从数据库取出后没有再转义，直接拼进了新的 SQL。

典型场景：注册时用户名存入 admin'-- ，登录时正常；但修改密码时，系统从数据库读出这个用户名拼接到 UPDATE 语句中，注释掉 WHERE 条件，把 admin 的密码改掉。

CTF 中看到“注册 → 登录 → 修改资料 / 修改密码”的流程，就要警惕二次注入。

题型七：二次注入 —— 注册时“埋雷”，改密时“引爆”

  2. 登录这个账号，一切正常。
  3. 进入修改密码或修改资料页面，系统从数据库读出 admin'-- 并拼进 UPDATE 语句：

-- 注释掉后面的 WHERE 条件，结果所有用户的密码都被改了，或者 admin 的密码被覆盖。

判断信号：注册、个人资料、修改密码之间形成闭环，且返回了“用户名已存在”或资料回显。

题型八：MySQL 列截断（Column Truncation）

注册表单中用户名列是 VARCHAR(20)，MySQL 会静默截断超长字符串。注册一个超长的 admin + 大量空格 + x 的用户名，存入数据库时被截断为 admin，于是创建了一个“重复的 admin”行，用攻击者自己的密码就能登录 admin。

CTF 中出现“注册后直接登录成功，但原本 admin 密码未知”的场景，可以留意这个方向。

六、防御：知道怎么打，才知道怎么防

  • 预编译（PreparedStatement / PDO）：把 SQL 结构和数据彻底分开，是最有效的防线[reference:24]。
  • 白名单校验：对 ORDER BY 的列名、LIMIT 的数字等不能参数化的位置，用白名单限制。
  • 最小权限：数据库连接用户不给 FILE、UPDATE、DELETE 等不必要权限。
  • 关闭详细报错：生产环境不要回显数据库错误信息，增加报错注入的门槛。
  • WAF 只能辅助，不能替代代码层的根本修复。

七、总结

SQL 注入的 CTF 解题主线可以压缩成一句话：先判断闭合和回显类型，再按“联合 → 报错 → 布尔 → 时间”的顺序选手法，最后用 information_schema 脱库。

真正拉开差距的不是背了多少 Payload，而是理解每一步为什么这么做：

  • ORDER BY 为什么能猜列数？
  • updatexml 为什么能把数据带出来？
  • 二次注入为什么“存的时候安全、用的时候不安全”？

把这三件事想明白，再遇到新题，只是换了一个过滤条件而已。
